**Skills** 是你在 Agent tab 里用 `/` 触发的短 prompt —— 每个 Skill 改变 AI 这一次回复的工作方式。OpenCockpit 内置 **14 个可见 Skills**(`/qa /spec /fx /ex /go /cg /cc /cr` 模式,外加 `/html /new-branch /skillify /ss /dl /bot`);你也可以写自己的 `SKILL.md` 文件,同样的方式装上。两种 Skills 共用一个 `/` 菜单。

> 不要跟**笔记**（项目笔记编辑器）里的斜杠菜单搞混 —— 那个是标题/列表/表格之类的格式化菜单。聊天输入框只识别 Skills；在聊天里打 `/` 弹出的菜单是这些内置命令加你装过的 `/skill-name`。

## 内置 Skills

| 命令 | 意图 | 反问吗？ | 写代码吗？ |
|---|---|---|---|
| **`/qa`** | 精简 PRD：目标、范围、假设和决策 | 有待决策项时 | ❌ 否 |
| **`/spec`** | 可供实现的规格设计 | ✅ 仅关键决策 | ❌ 否 |
| **`/fx`** | 根因证据链、修复选项和验证方法 | 需要选择修复方案时 | ❌ |
| **`/ex`** | 有证据支撑的深度分析 | ❌ | ❌ |
| **`/go`** | 实现已确认工作，分步验证并记录决策 | 阻塞或难以撤销的选择 | ✅ 是 |
| **`/cg`** | CodeGraph 项目探索 | ❌ | ❌ |
| **`/cc`** | 操作 CLI：浏览器、终端观察、代码图谱 | 目标仍不明确时 | ❌（操作 CLI） |
| **`/cr`** | 完整代码审查(静态 + 动态) | ❌ | ❌(只审查出 findings,不改代码) |
| **`/html`** | 生成接了 [bash SDK](/zh/docs/agent/html-apps/) 的本地交互式 React 应用 | 先确认需求和目录 | ✅ 是 |
| **`/new-branch`** | 基于最新 `origin/main` 建分支并验证同步 | 命名或工作区状态需要选择时 | ❌（只动 git） |
| **`/skillify`** | 评估并提炼已验证的可复用工作流 | 保存目录缺失时 | ✅ 值得提炼时才写 |
| **`/ss`** | 一句话找回过去的会话 —— 不限项目、引擎、日期 | ❌ | ❌(只搜索) |
| **`/dl`** | 委派到新会话，默认立即返回，`--wait` 等结果 | 缺少必要任务信息时 | 由子会话执行任务 |
| **`/bot`** | 创建并注册带长期上下文的 Bot | 先确认角色、名称和目录 | 写入 Bot 文件 |

前 8 个是**模式** —— 改变 AI 这一次回复的工作方式,下面每个都有单独一节。其余 6 个是任务命令,指令都在各自的 SKILL.md 里,没有需要配置的东西。`/ss` 和 `/dl` 跨会话工作,下面也各有一小节。

## `/qa` —— 改任何东西前先澄清

适用：你即将要求一个代码改动，但需求还不够清晰。

```text
/qa 我想让文档侧栏行为更像 Cursor 的
```

AI 会：

1. 产出精简 PRD，明确问题、目标、成功标准、范围、约束和假设。
2. 对待决策项给出编号选项、收益、代价和建议。
3. 收到回答后只输出变化和剩余决策。

这个模式澄清“做什么、为什么”，不设计方案、不写代码。需要可供实现的具体规则时，再用 `/spec`。

## `/spec` —— 把已确认需求写成规格

适用：需求方向已经确认，需要明确行为、接口契约、边界和验收标准。输入可以是 `/qa` 产物、文档或当前对话，不要求先用 `/qa`。

```text
/spec 把已确认的侧栏需求整理成规格
```

AI 会核实相关集成假设，将验收场景关联到行为规则，只对尚未解决的关键决策提问，不执行功能实现。默认在对话中输出，要求保存时才写入文档；回答决策也不代表授权实现。

## `/fx` —— 构建 bug 证据链

适用：你有一个症状，需要追到根因。

```text
/fx 文档页在某些 session 的代码块里渲染成 ",[object Object],"
```

AI 会：

1. 形成假设。
2. 检查涉及的代码路径。
3. 把证据列出来 —— 什么触发什么，逐行。
4. 明确根因和影响范围，对比修复选项，给出验证方法。未证实的链路标为假设，不修改代码。

诊断敲定后配合 `/go`。

## `/ex` —— 深度分析，结论先行

适用：你需要对复杂问题得出有证据支撑的结论，不希望被反问打断。AI 会先给结论，再列出带来源的发现，并按需补充选项、风险和待确认项；缺失信息会注明其影响，继续分析，不修改代码。

```text
/ex 对比这个接口的三种缓存策略
```

适合复杂问题分析、方案对比和机制解释。简单问题直接回答；追问时只输出有变化的部分。

## `/go` —— 落地改动

适用：方案已定，你要 AI 真的去做。

```text
/go 给 /api/heavy-endpoint 加上 60 秒 TTL 的 Redis 缓存
```

`/go` 模式：

1. 以给定的规格、简报或当前对话中的约定为输入；无法推断成功标准时先问一次。
2. 分小步实现，通过命令、请求或测试实际验证每一步。
3. 验证失败最多重试 3 次，之后标记阻塞，继续不依赖它的工作。
4. 规格未覆盖且容易撤销的选择自行决定并记录；难以撤销的选择、破坏性操作或阻塞信息缺失时才提问，不为阶段完成而等待确认。
5. 最后跑一遍完整用户流程，报告结果、决策笔记链接和遗留项。笔记保存在仓库外，30 天未更新后清理。

写代码时间最多的就是这个模式。需求或分析收敛后使用；需要明确行为和验收规则时，可先用 `/spec`。

## `/cg` —— 把项目当图来探索

适用：你需要理解代码结构而不想把所有东西 grep 一遍。

```text
/cg 哪些 handler 调用了数据库适配器？
```

`/cg` 把 AI 切到读 Cockpit 本地的 **CodeGraph** —— 一份项目的结构索引（谁调用什么、什么调用谁、哪些文件经常一起改），不再让它对每个文件做暴力 grep。回答更快，也更聚焦。

图在你第一次问的时候自动构建。没有安装步骤,不用配项目。当前支持 TypeScript / JavaScript / Python / Go / Rust(基于 tree-sitter,不依赖 LSP,所以 Go/Rust 不需要装 language server)。

## `/cc` —— 通过 CLI 操作 Cockpit

适用:代码改完了,要让 AI **真的**去跑一下、看 UI、抓网络、确认行为对了。

```text
/cc 终端: cockpit terminal abc123
    浏览器: cockpit browser xyz789
    测一下 chat 输入框的发送功能,验证消息能正确入库且 UI 实时刷新
```

`/cc` 把 AI 切到**操作 Cockpit CLI** 的模式 —— 把 `cockpit terminal <id> output` 拿终端输出、`cockpit browser <id> click/type/network` 等驱动浏览器气泡当作主要工具。有**短 ID** 时可以直接提供；没有时，AI 会列出当前项目的气泡，按标题或 URL 匹配，也可以自行打开浏览器气泡并在用完后关闭。终端仅支持只读观察。默认使用 `cockpit` 操作生产实例；`/cc dev …` 或明确指定 `cockpit-dev` 才操作开发实例。

通常配合 [`/go`](#go-落地改动) 使用 —— `/go` 写完代码,`/cc` 验证它确实活在用户那一侧。详细 walkthrough 见[快速开始](/zh/docs/get-started/quickstart/#端到端验证-console-拉起服务-cc-测试)。

## `/cr` —— 完整代码审查(静态 + 动态)

适用:一个 PR 改完了,要一次性做完整审查 —— 既扫静态对错,也挖时序 / 状态 / 并发这类逐行看不出来的动态行为。

```text
/cr 审一下当前分支相对 main 的改动
```

`/cr` 把审查拆成两路:**静态三角校验**(拿每处改动和 意图 / 输入域 / 周遭契约 三个参照交叉定位)广扫全部改动;碰到状态 / 时序 / 并发的切片,再走**动态推演**(画状态图 + 时间线,评估 6 类动态风险)。实际审查在干净的 subagent 里跑,主会话只派发和合并,最后输出结论、方案图、按严重程度排序的问题和覆盖范围。

自包含一套方法论,不依赖外部工具;微小改动由一个审查者完成，默认分别进行静态和动态审查；是否动态建模取决于涉及的行为。显式传入 `hard` 时，按动态切片分配独立审查者。通常配合 [`/go`](#go-落地改动) 使用 —— `/go` 落地完,`/cr` 兜一遍质量。

## `/ss` —— 找回过去的会话

适用:你记得聊过什么,但记不清是在哪个项目、哪个引擎、哪一天。

```text
/ss 上次讨论本地接口 CSRF 的那个会话
```

AI 不会拿你这句话原样去搜。它先展开成几个关键词(技术话题中英文都写,再加同义词),搜索 Cockpit 能读到的全部会话 —— 所有项目、所有引擎(Claude、Codex、DeepSeek、Kimi、GLM、Ollama)、不限日期 —— 读命中片段后给出 1–3 个候选。每个候选带一个会话链接:点开后 Cockpit 切到对应项目,并在 Agent 面板打开该会话。

底层:Cockpit 把每个会话的用户输入和 AI 回复抽成纯文本(不含工具输出、系统提示、图片),增量存放在 `<数据目录>/search-corpus`,用 ripgrep 搜索,所以 `快照` 这样的两字中文词也能命中。subagent 记录不收录。一台机器上第一次搜索时要先建这份文本,可能需要几秒。接口:`GET /api/sessions/search`。

## `/dl` —— 委派子任务，可选等待

适用:某件事应该在另一个目录做、更适合另一个引擎,或者只是不想让它堵住当前对话。

```text
/dl 让 codex 去 api 项目里把那个时好时坏的日期测试修掉
```

AI 会写一份自包含的任务说明(子会话看不到你们的对话),在目标目录用选定的引擎新开一个会话,并立即拿到回执 —— 引擎、目录、会话 ID、链接。它会在回复里复述回执,然后继续当前对话。子会话像普通会话一样独立运行,随时点链接进去看或接手。

加上 `--wait` 会等待子会话结束，并在当前轮使用其结果继续工作；不带该参数时立即返回。

之后问一句「刚才委派的那个任务怎么样了」,AI 会找到回执 —— 在当前对话里,或者走 `/ss` 的搜索流程 —— 然后查询子会话状态:`running`(运行中)、`done`(完成)、`failed`(失败)或 `incomplete`(被停止或中断,点进去继续即可),并附上它最后一条回复。

- **服务端不存任何委派记录。** 发起会话里的回执就是记录;状态从子会话所在引擎自己的会话记录里读出。
- **引擎:** `claude`、`codex`、`deepseek`、`kimi`、`glm`、`ollama`。不指定时沿用发起方会话正在用的引擎(判定不出来才回落 `claude`);目标引擎需已配置;目录不存在之类的错误会立即返回。
- **并发上限:** 默认最多同时运行 4 个委派会话(`COCKPIT_DELEGATE_MAX`,见 [CLI 参考](/zh/docs/reference/cli/#环境变量)),超出直接拒绝,不排队。
- **不是 subagent 的替代品。** 同一仓库里的并行工作,Claude 自带的 subagent 通常更合适。`/dl` 面向的是其他目录、其他引擎,以及你能打开、能接手的会话。

接口:`POST /api/sessions/delegate`、`GET /api/sessions/status`。

## 模式：串成链

典型的端到端任务把模式串起来：

```text
/qa 我们要给重接口加缓存                        ← 澄清
/cg 哪些 handler 碰了 /api/heavy-endpoint？     ← 发现代码
/fx 为什么这个接口慢？                           ← 分析
/go 加上 60 秒 TTL 的 Redis 缓存                ← 执行
/cr 审一下这次改动                              ← 审查
```

入口取决于你手里有什么：

- 模糊目标 → `/qa`
- 症状 → `/fx`
- 代码相关问题 → `/cg`
- 想要不被打断的分析 → `/ex`
- 需求需要行为、契约和验收标准 → `/spec`
- 方案已定 → `/go`
- 改完想审查 → `/cr`
- 想找回以前的对话 → `/ss`
- 活儿该在别的项目或别的引擎上做 → `/dl`

> 上表列出了可见的内置 Skills。内部流程 `bot-run` 和 `bot-turn` 不显示在 `/` 菜单中。要做你自己的重复工作流，看下面的[自定义 Skills](#自定义-skills) —— 它们出现在同一个 `/` 菜单里，叫 `/skill-name`。

## 自定义 Skills

自定义 Skills 是你自己的斜杠命令 —— 跟上面的内置模式同一回事，只是 prompt 是你自己写的。在聊天里以 `/你的-skill-名` 触发。

如果你发现每周都在向 Claude 粘贴同一段长指令 —— "按这几条具体规则审查这个 PR"、"按这个格式总结提交"、"跟着这个调试 checklist 走" —— 把它做成一个 Skill，一次性、永久复用。

### Skill 是什么

一个 Skill 就是一个名为 `SKILL.md` 的 Markdown 文件。文件顶部是一小段 YAML 风格的元信息，给这个 skill 命名和描述；文件正文是 prompt 本身。

最简示例：

```markdown
---
name: pr-review
description: 按我们团队的 checklist 审查 PR
icon: 🔍
argument-hint: "[PR 编号或 URL]"
---

你在审查我们团队的一个 pull request。请检查：

1. 测试有没有覆盖新行为
2. 公共 API 有没有破坏性改动
3. changelog 里有没有迁移说明
4. 提交信息是不是大白话

输出结构化评审：摘要、阻塞项、建议、通过/拒绝。
```

这个文件可以放在你电脑的任何位置 —— Cockpit 不会移动它。

| 字段 | 必填？ | 作用 |
|---|---|---|
| `name` | 是 | 斜杠触发名。这里就是 `/pr-review`。空格变破折号。 |
| `description` | 是 | 聊天下拉菜单里显示的一行说明。 |
| `icon` | 可选 | 下拉里名字旁边的 emoji。 |
| `argument-hint` | 可选 | 提示文本，比如 `[PR 编号或 URL]`，下拉里显示，提醒你斜杠命令后该打什么。 |

### 在 Cockpit 里安装一个 Skill

1. 打开 **Skills** 模态（从侧栏或应用菜单）。
2. 点 **+ 添加 Skill**。
3. 粘贴**你 SKILL.md 文件的绝对路径**（比如 `/Users/me/skills/pr-review/SKILL.md`）。
4. 回车。

Cockpit 校验文件存在并读取 frontmatter。如果有问题（文件不存在、frontmatter 格式错），skill 卡片上会显示 `[Invalid]` 角标。

要删除某个 skill，鼠标悬停到卡片上点垃圾桶图标。

> Cockpit 不复制文件 —— 只记住路径。如果你移动或重命名了 SKILL.md，这个 skill 就不工作了，要删掉旧的、用新路径重新加。

### 使用一个 Skill

装好后在任意 Agent tab 打 `/`。聊天下拉显示两个分组：

- **Commands** —— 可见的内置命令。
- **Skills** —— 你装过的全部，带图标和参数提示。

输入即过滤,回车或 Tab 插入。聊天输入框被填成 `/你的-skill-名 `(末尾带空格,方便你接着打参数)。打完参数回车发送。

AI 收到的是你 skill 的 prompt 正文加上你的参数 —— **斜杠后面打的所有内容**都会作为 argument 拼到 skill body 之后。没有特殊权限、没有第二个菜单,就是"每次粘同样 prompt"的更优雅版本。

### 跟团队分享

一个 Skill 就一个文件。要跟队友分享，把 SKILL.md 发给他（或推到一个共享仓库）。他用同样的方式加 —— 粘路径、完事。

有些团队会维护一个共享的 `~/team-skills/` 目录，每个人的 SKILL.md 各放一个子目录里。这样加新 skill 就是 `git pull` 然后在 Cockpit 里 **+ 添加 Skill**。

### 跨 tab 即时同步

你在一个 tab 加或删 skill,所有其它已经打开的 Cockpit tab 的 `/` 菜单**立刻**更新 —— 不需要刷新。底层走浏览器原生的 `BroadcastChannel('cockpit-skills')`,纯客户端、零延迟、不经服务端。
